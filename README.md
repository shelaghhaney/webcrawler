# Wikipedia Robotics & AI Web Crawler

A concurrent Go-based web crawler and scraper built on the
[Colly](https://github.com/gocolly/colly) framework.  It collects plain-text
content from ten Wikipedia articles on intelligent systems and robotics, and
writes the results to a JSON Lines (`.jl`) file ready for ingestion into a
knowledge base.

## Overview

The firm's original Python/Scrapy solution visits Wikipedia URLs sequentially
and is slow.  This project replaces it with a Go program that:

- Visits all target Wikipedia URLs **concurrently** via Colly's async
  collector and a goroutine-based worker pool.
- Uses **Colly's CSS selectors** (`h1#firstHeading`, `#mw-content-text p`) to
  cleanly target article titles and body paragraphs, stripping all HTML markup.
- Filters short, non-substantive text fragments (navigation labels, lone
  captions, etc.) before writing output.
- Writes every scraped article as a single JSON object on its own line,
  producing a standard **NDJSON / JSON Lines** (`.jl`) file.
- Logs all activity to `crawler.log` and optionally writes CPU/memory profiles.

## Installation & Build

```bash
# 1. Clone the repository
git clone https://github.com/shelaghhaney/webcrawler.git
cd webcrawler

# 2. Download dependencies (requires internet access)
go mod tidy

# 3. Build the executable
go build -o crawler ./cmd/crawler/

# On Windows the binary is named automatically:
# go build -o crawler.exe ./cmd/crawler/
```

`go mod tidy` will fetch Colly v1 and its transitive dependencies
(`goquery`, `antchfx/htmlquery`, `antchfx/xmlquery`, `gobwas/glob`,
`kennygrant/sanitize`, `temoto/robotstxt`, `saintfish/chardet`, and
`golang.org/x/net`).

## Usage

### Basic run (defaults)

```bash
./crawler
```

Crawls the 10 target Wikipedia pages, writes results to `results.jl`, and
logs progress to `crawler.log`.

### Custom output path

```bash
./crawler -out knowledge_base.jl
```

### With CPU and memory profiling

```bash
./crawler -out results.jl -cpuprofile cpu.prof -memprofile mem.prof
```

Inspect profiles with the standard Go tool:

```bash
go tool pprof cpu.prof
go tool pprof mem.prof
```

### All CLI flags

| Flag          | Default      | Description                          |
|---------------|--------------|--------------------------------------|
| `-out`        | `results.jl` | Path for the JSON Lines output file  |
| `-cpuprofile` | *(disabled)* | Path for optional CPU profile        |
| `-memprofile` | *(disabled)* | Path for optional heap memory profile|

### Target URLs

Defined in `cmd/crawler/main.go`:

```go
var targetURLs = []string{

    "https://en.wikipedia.org/wiki/Reinforcement_learning",

    "https://en.wikipedia.org/wiki/Intelligent_agent",
    "https://en.wikipedia.org/wiki/Software_agent",

    "https://en.wikipedia.org/wiki/Applications_of_artificial_intelligence",
    "https://en.wikipedia.org/wiki/Android_(robot)",

```

Add or remove entries freely; the program adapts automatically.

## Testing

Run **all unit tests** with verbose output:

```bash
go test ./... -v
```

Run tests with the **race detector** (recommended before submission):

```bash
go test -race ./...
```

Generate an HTML **coverage report**:

```bash
go test ./... -coverprofile=coverage.out
go tool cover -html=coverage.out
```

### What the tests verify

**`internal/parser`** — pure text-processing logic, no network needed:

| Test | What it checks |
|------|----------------|
| `TestCleanText_CollapsesSpaces` | Multiple spaces/tabs → single space |
| `TestCleanText_CollapsesNewlines` | 3+ newlines → two newlines |
| `TestCleanText_NormalisesWindowsLineEndings` | CRLF → LF |
| `TestCleanText_TrimsLeadingTrailingSpace` | Leading/trailing whitespace removed |
| `TestCleanText_EmptyString` | Empty input → empty string |
| `TestIsUsefulParagraph_AcceptsLongParagraph` | ≥5 words → true |
| `TestIsUsefulParagraph_RejectsSingleWord` | 1 word → false |
| `TestIsUsefulParagraph_RejectsEmptyString` | Empty → false |
| `TestIsUsefulParagraph_AcceptsExactlyMinWords` | Exactly 5 words → true |
| `TestIsUsefulParagraph_RejectsFourWords` | 4 words → false |

**`internal/crawler`** — exercises Colly end-to-end through a mock
`httptest.Server` (no live network required):

| Test | What it checks |
|------|----------------|
| `TestCrawlURLs_ExtractsTitleAndBody` | Title and body extracted correctly via Colly CSS selectors |
| `TestCrawlURLs_CrawlsMultiplePagesConcurrently` | 3 pages fetched concurrently within 5 s |
| `TestCrawlURLs_FiltersShortParagraphs` | <5-word paragraphs excluded |
| `TestCrawlURLs_EmptyInputReturnsEmptySlice` | Empty URL list → empty result |
| `TestCrawlURLs_HTTP404PageIsSkipped` | 404 responses logged and skipped gracefully |

## Profiling & Monitoring

- **Structured log** (`crawler.log`): microsecond-timestamped entries for
  every URL visited, page scraped, and error encountered.
- **CPU profile** (`-cpuprofile`): which functions consume the most CPU.
- **Memory profile** (`-memprofile`): heap snapshot taken after a forced GC at
  program exit, minimising noise from uncollected objects.

## Output Format

A **JSON Lines** (NDJSON) file — one complete JSON object per line, no
trailing commas, conforming to [jsonlines.org](https://jsonlines.org/).

```json
{"url":"https://en.wikipedia.org/wiki/Robotics","title":"Robotics","body":"Robotics is an interdisciplinary branch..."}
{"url":"https://en.wikipedia.org/wiki/Robot","title":"Robot","body":"A robot is a machine..."}
```

| Field   | Type   | Description |
|---------|--------|-------------|
| `url`   | string | Canonical Wikipedia URL |
| `title` | string | Article title from `h1#firstHeading` |
| `body`  | string | Plain-text content; paragraphs separated by `\n\n` |

Quick inspection commands:

```bash
# Pretty-print the first record
head -1 results.jl | python3 -m json.tool

# Count scraped pages
wc -l results.jl
```

## Performance: Go vs Python/Scrapy

### Python/Scrapy (sequential baseline)

The original Scrapy spider visits URLs one after another.  With Wikipedia
round-trips of roughly 200–400 ms each, scraping 10 pages takes approximately
**3–5 seconds**.

### Go + Colly (concurrent)

Colly's async collector dispatches all requests concurrently (up to
`Parallelism=5` at a time).  Total wall-clock time is bounded by the *slowest
single request*, not the *sum of all requests*.  On the same network the Go
crawler completes in approximately **0.5–1.5 seconds** — a **3–5× wall-clock
speedup** for this workload.

### Why Go + Colly is faster

| Factor | Python/Scrapy | Go + Colly |
|--------|--------------|------------|
| Concurrency model | Twisted async event loop (single thread) | True OS goroutines via `sync.WaitGroup` + Colly async |
| Startup overhead | Python interpreter + Scrapy framework init | Compiled binary, near-zero startup |
| Memory per goroutine | N/A | ~2–8 KB (vs ~1 MB per OS thread) |
| GIL contention | Yes — limits true parallelism | No GIL |
| HTML parsing | lxml / BeautifulSoup | Colly → goquery → `x/net/html` (compiled) |

At larger scale — hundreds or thousands of URLs — the advantage widens:
Python's event loop and GIL become bottlenecks while Go's scheduler continues
to scale linearly across all available CPU cores.

## Design Notes

### Why Colly?

Colly provides a clean, idiomatic Go API for web scraping: CSS and XPath
selectors via `OnHTML`, built-in rate limiting, robots.txt support, and an
async/parallel execution model that maps naturally onto Go's goroutine
scheduler.  It replaces the boilerplate of manual `net/http` + `sync` code
while keeping the codebase readable.

### Content extraction strategy

Two Colly CSS selectors target Wikipedia's stable HTML structure:

- `h1#firstHeading` — article title
- `#mw-content-text p` — body paragraphs inside the article content div

Narrowing to `#mw-content-text` avoids boilerplate paragraphs from headers,
footers, and side-navigation boxes.

### Polite crawling

A configurable `RequestDelay` (default 500 ms) is applied per-domain via
Colly's `LimitRule`, and the `User-Agent` header identifies the bot by name
and purpose — following Wikipedia's bot policy and the Robots Exclusion
Protocol spirit.

### Error handling

Non-200 HTTP responses and network failures are logged via `OnError` and
skipped; the program always writes a partial result file even if some pages
are unavailable.
